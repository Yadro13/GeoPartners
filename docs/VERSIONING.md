# Версії та журнал змін

## Поточна модель

GeoPartners використовує Semantic Versioning у форматі `MAJOR.MINOR.PATCH` і
журнал [CHANGELOG.md](../CHANGELOG.md) у структурі Keep a Changelog.

- `package.json` містить версію коду в репозиторії.
- Анотований Git tag `vMAJOR.MINOR.PATCH` фіксує точний release commit.
- `CHANGELOG.md` описує користувацькі, операційні та безпекові зміни.
- Railway deployment і середовище не входять до номера версії: той самий release
  commit спочатку перевіряється у staging, а потім може бути перенесений у
  production.

Проєкт ще не передано в production замовника, тому використовується лінійка
`0.x.y`. Погоджений перший production-реліз отримає `1.0.0`.

## Коли змінювати номер

- `PATCH` — сумісне виправлення помилки, безпекове посилення або мала UX-правка
  без зміни контрактів і моделі даних.
- `MINOR` — нова сумісна функція, новий звіт, поле, API або суттєвий робочий
  сценарій. До `1.0.0` сюди ж належить контрольована несумісна зміна з міграцією
  та явним описом у changelog.
- `MAJOR` — після `1.0.0` несумісна зміна API, даних або поведінки, яка потребує
  окремого плану переходу.

Зміни лише в документації не вимагають нового release-номера. Кілька пов'язаних
змін можна випускати одним раціональним батчем.

## Робочий процес

1. Кожен завершений функціональний батч додається до секції `Unreleased` у
   `CHANGELOG.md`. Формулювання описує результат для користувача або оператора,
   а не перелік змінених файлів.
2. Перед релізом виконуються lint, typecheck, unit/ops/browser tests, build і
   релевантна staging-перевірка.
3. Обирається номер за правилами вище; версії у `package.json` і
   `package-lock.json` синхронізуються.
4. Секція `Unreleased` переноситься у секцію `[X.Y.Z] - YYYY-MM-DD`.
5. Release commit отримує анотований tag `vX.Y.Z`; commit і tag публікуються в
   GitHub. Для production просувається саме перевірений tag/commit.
6. Міграції БД, нові variables, backup/restore та rollback-умови фіксуються в
   changelog або release notes, якщо вони потрібні оператору.

## Відновлена історія

До 6 серпня 2026 року окремого changelog і tags не було. Межі `0.1.0`-`0.5.0`
відновлено за атомарною Git-історією, датованими staging-перевірками,
`ACCEPTANCE_CHECKLIST.md`, backlog і реєстром додаткових робіт:

| Версія | Git-межа | Зміст віхи |
|---|---|---|
| `0.1.0` | `0780b46` | Початковий статичний прототип |
| `0.2.0` | `41d0b69` | Повний застосунок, Railway/CI, ZIP та правила накладань |
| `0.3.0` | `b506cbb` | Staging-стабілізація, email transports і production handover |
| `0.4.0` | `02d5240` | Права доступу, довідники, Google linking і multi-admin review |
| `0.5.0` | `d42ea2a` | Етапи, три мови, матричні звіти та узгоджений workspace |
| `0.6.0` | release commit | Масовий імпорт, універсальні результати й фундамент знімків |

Ці межі документують staging-віхи та не означають, що відповідні версії раніше
встановлювалися у production. Від `0.6.0` tags і changelog ведуться як частина
звичайного release-процесу.
